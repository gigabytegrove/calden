# Calden 1.4.0 – completion and deployment requirements

The 1.3.8 server / 1.3.9 Android interfaces are the approved baseline. This
release work focuses on **Notifications, scheduling conflicts and Monita**.
Previously approved calendar, bill, chore, profile and widget behavior must not
be redesigned or removed.

## 1. Notification delivery

Calden uses three complementary delivery paths:

1. **Live authenticated WebSocket:** immediate foreground/connected delivery and
   a non-sensitive change marker that refreshes mobile and widget caches.
2. **Native Firebase Cloud Messaging (FCM, optional):** delivers per-user Android
   data notifications while the application's WebSocket is absent. Server-side
   OAuth credentials are used only by Calden; the Android app receives its
   public Firebase client configuration through an authenticated API.
3. **Durable catch-up:** REST inbox and WorkManager polling, plus existing local
   device event reminder scheduling, continue when FCM is unconfigured or an
   Android device is temporarily unreachable.

FCM is not operational **until an administrator configures a Firebase project
and matching service credentials**. Merely upgrading Calden does not enable it.
Push delivery remains subject to Android permissions, network conditions and
operating-system restrictions. No delivery can be guaranteed in flight mode.

### Configure native push, without an additional container

Register Android application ID `com.gigabytegrove.calden` under a Firebase
project. Enable the Firebase Cloud Messaging API. Obtain the Android app's
Firebase application ID, project ID, sender number and web API key from Firebase
project settings. Generate a Firebase service-account JSON credential with
permission to send FCM messages. The service credential remains *on the
Calden server only* and must be secured as a read-only file with mode 0600.

Set these environment variables for the **existing Calden service**:

| Variable | Value |
|---|---|
| `CALDEN_FCM_SERVICE_ACCOUNT_FILE` | Absolute path inside the Calden process/container to mounted service-account JSON |
| `CALDEN_FCM_PROJECT_ID` | Firebase project ID matching that credential |
| `CALDEN_FCM_SENDER_ID` | Firebase project sender number |
| `CALDEN_FCM_ANDROID_APP_ID` | Android app Firebase application ID |
| `CALDEN_FCM_API_KEY` | Android application's Firebase API key (public client identifier) |

Do **not** put the JSON credential, private key, or bearer tokens into Android
assets, `docker-compose.yml`, logs, the database plaintext, GitHub commits,
or an HTTP request from the browser. Back up the Calden data directory's
`.jwt-secret`: it is also needed to decrypt registered device tokens.

After configuration, authorized admin diagnostics are available at
`GET /api/notifications/push-diagnostics`. The Android client requests
`GET /api/notifications/push-config` and registers per-installation token
with `POST /api/devices`. Revoke devices using
`DELETE /api/devices/{id}`. Queued deliveries are persisted in PostgreSQL,
claimed transactionally, retried with exponential backoff, and capped.

**Acceptance:** sign in on two distinct Android devices, grant notifications,
send separate assignments, updates and bill reminders, force-stop app service
*without force-stopping the entire app*, test disconnected/reconnected service,
and verify per-user authorization, one visible notification per UUID,
notification inbox coherence, reboot recovery, revocation and token rotation.
Android force-stop can prevent OS-mediated background delivery until user relaunch.

## 2. Scheduling conflicts and private busy time

On web and Android, the event editor previews overlaps before saving a
non-Bill Pay appointment. An overlap produces a **warning**; the creator can
choose to save anyway. Changes to time/assignees invalidate a previous
approval. Events are compared using half-open intervals, so an event ending at
14:00 never conflicts with one beginning at 14:00.

Household members can manage private unavailable periods under their account.
Busy labels are readable only by their owner. Conflict results intentionally
expose generic busy intervals without title or private note. Members may not
query another person's availability; Planners and admins may check people
assigned to an appointment.

Recurrence previews are bounded to a 90-day planning horizon to prevent
unbounded calculation. Overrides/cancelled occurrences must be excluded from
the original series. **An absence of conflicts beyond the preview horizon is
not proof of future availability.**

## 3. Monita

No external helper container is required. An administrator creates a scoped
service account in Monita with `channel:read` and `message:write` privileges
and grants it access only to the intended household notification channel.

In Calden web Settings → Integrations → Monita:

1. Enter the Monita server URL and the scoped **SA.** service token.
2. Choose **Load channels**; choose a channel accessible to that token.
3. Choose **Connect & verify**. Calden verifies token access, sends a test
   notification to that channel, and saves the token encrypted only on success.
4. Choose **Disconnect** to turn off Monita and remove the saved token.

Legacy channel tokens are preserved as a compatibility path. Standard family
reminders use Monita; individual Android account notices use Calden native
notifications. Monita reminder deliveries have per-occurrence deduplication,
transactional leases, bounded backoff, and cancellation/recurrence filtering.

## Release verification gate

- Server: Go tests, `go vet`, new clean-install migrations, browser smoke,
  Docker smoke, backup/restore regression, Monita mock integration tests,
  private-time authorization tests, push-queue tests all green on release SHA.
- Android: Kotlin compile, unit tests, versioned APK, APK signature/manifest
  inspection, and two-phone actual testing including 1.3.9 approved widgets.
- FCM: credentials configured and real background delivery / account-switch
  isolation verified. Otherwise label FCM **configured optional / unverified**
  rather than calling this path complete.
- Ensure both repositories use VERSION **1.4.0**, produce matching artifacts,
  and tag the same reviewed source state only after passing the above checks.

Source commits are not proof of successful Android build, push delivery or
integration with a particular Monita installation.
