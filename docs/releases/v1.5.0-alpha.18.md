# Calden v1.5.0-alpha.18 — Stop tracking from resetting after every update

## Root cause fixed
Calden's binary-only in-app update performs a syscall.Exec. The old tracking worker initialized its in-memory status to `pending` on every restart, even when Node and Chromium were already installed, tested and operational. The Packages screen exposed that pending flag before the asynchronous worker finished verifying runtime dependencies.

## Implemented
- **Persist verified runtime readiness** in the existing /data volume, using a private receipt with the actual executable path, size, modified timestamp and permissions for Node, scraper CLI and Chromium. Reuse verified readiness after a hot update or container restart without reinstalling the tracker.
- **Synchronous local startup verification** when migrating an older deployment with no receipt, before serving the Packages UI. This does not download dependencies during startup.
- **Preserve the repaired legacy runtime**, even if the original Docker image still has a broken pre-installed CLI.
- **Eliminate conflicting Packages health checks.** The HTTP endpoint now reports the worker's verified runtime state instead of running a second scanner with a shorter, unreliable 6-second deadline.
- **Detect actual damage.** Missing executables invalidate readiness; the background worker re-probes periodically and repairs the runtime.
- **Meaningful failure diagnostics.** If a real download, unpack or execution failure occurs, display the bounded underlying reason in Packages and log it, rather than indefinitely repeating "preparing tracking automatically".
- **Avoid repeated unnecessary carrier checks** when a healthy runtime survives the update. A genuine repair still queues eligible shipments once.
- Honor the Package Tracking opt-in setting. Never install a browser for households with the feature disabled.

## Verification requirements
The release workflow runs Go/PostgreSQL and DOM tests, first-run Docker and UI checks, native ARM64 and AMD64 tracking runtimes, archive limit and checksum verification, and multi-architecture Docker publication. It only releases after all gates pass.

## Real-host acceptance
Published CI artifacts do not establish whether a particular legacy container can download a large repair runtime or a particular carrier responds. Those require installation on the actual host. When recovery is impossible, Calden now reports the underlying error instead of hiding it behind a generic preparing notice.
