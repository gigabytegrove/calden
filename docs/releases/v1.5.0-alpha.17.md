# Calden v1.5.0-alpha.17 — Automatic tracker repair and accurate carrier history

This release builds on the approved alpha.16 interface and preserves existing calendars, bills, household members, meals, packages, and settings.

## Repair broken carrier tracking inside the existing container
- Calden verifies that both its Node-based scanner and Chromium can **execute**, not merely that their files exist.
- If a legacy container contains broken tracker files, the application can recover by installing and selecting a separately verified runtime in the existing persistent data volume. No host package installation, privileged Docker access, or second service is required.
- A working bundled runtime is retained. Calden periodically rechecks runtime health, detects failures, and retries automatic repair.
- Package Tracking stays off by default. While disabled, no large tracker download occurs. Refresh during recovery is queued rather than consuming a manual cooldown.

## Actual tracking history rather than inferred activity
- Carrier scans with unknown or newly introduced stage names are preserved in Tracking history with **Unknown** as their status, instead of silently disappearing.
- If the current status is missing, Calden selects the latest independently timestamped recognized carrier event. An undated or unrecognized event cannot fabricate a shipment status.
- **Carrier scan** indicates an actual carrier checkpoint; **Carrier status** indicates a reported current status without an actual scan. The database migration also corrects already-saved status-only observations without discarding tracking history.
- Tracking history remains paginated, accessible to authorized shared viewers, and independent from edit/delete actions.
- Carrier lookups still respect the three-hour polling interval and two-minute manual check cooldown; delivered shipments stop polling.

## Release gates
The automated release must pass the existing Go/PostgreSQL tests and browser/DOM regressions, build AMD64/ARM64 application updater archives, validate both standalone carrier-runtime archives under an unprivileged Alpine user, verify checksums, and publish a multi-architecture Docker image.

## Operational acceptance remains necessary
Publication alone cannot prove that a real carrier supplies live data for a specific number, that a legacy user's running container has been repaired, or that their in-place update succeeded. These must be checked against a real installation before declaring full production acceptance.
