# CalDen 0.1.0-alpha11.3

Alpha11.3 replaces the previous duplicate-repair assumptions with an explicit CalDen-side duplicate resolver.

## What changed

The earlier repair logic was still too dependent on Google UID relationships and export interpretation. That is not enough once older CalDen imports have already created multiple stored rows.

Alpha11.3 scans the events that are actually in CalDen and groups suspicious imported copies using their title, recurrence pattern, duration, dates, and calendar context.

For every group, the administrator can see the individual stored copies and select exactly which event CalDen should keep.

CalDen does **not** automatically decide that the earlier date, later date, older UID, newer UID, or newest database row is correct.

## Colquitt EMC-style case

A monthly imported event can exist in CalDen twice, such as one stored series producing October 6 and another stored series producing October 7.

Alpha11.3 presents both stored series as one possible duplicate group. The administrator can explicitly choose October 7 to survive and CalDen removes the October 6 series.

No Google re-import is required for that cleanup.

## Repair safety

- no calendar deletion
- no re-import during repair
- groups can be skipped
- typed confirmation is required
- the selected duplicate group is validated again inside the repair transaction
- only explicitly selected redundant event rows are removed
- compatible CalDen-side assignments, reminders, notifications, and Bill Pay data are merged into the chosen survivor

## Import behavior

Normal Google import still uses Google UIDs and explicit calendar mapping. The new resolver is intentionally separate from import so cleanup of already-bad CalDen data never has to guess what Google meant.

## UI

The old export-driven repair controls were removed from the primary cleanup workflow.

The repair panel now:

- scans CalDen directly
- shows possible duplicate groups
- shows each stored date and calendar
- labels the newest CalDen copy as a suggestion only
- lets the administrator choose the survivor
- supports skipping a group
- requires a typed `REMOVE N` confirmation

## Validation

CI reproduces a monthly recurring event stored twice on the 6th and 7th with different imported UIDs, selects the 7th as the survivor through the repair API, and verifies that:

- the 6th copy is removed
- the 7th remains
- the calendar remains intact
- no re-import is performed as part of the repair
